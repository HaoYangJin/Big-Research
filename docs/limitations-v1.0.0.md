# v1.0.0 的缺陷、限制与后续优先级

复核日期：2026-10-16。范围是 Git 标签 `v1.0.0` 的实现，以及其后的安装与文档核验。文档更新不代表已修复该标签的代码。现有验收记录见 [验证报告](validation-v1.0.0.md)。

v1.0.0 已有九阶段工作流、证据台账和检查点，但成熟度主要体现在流程约束与本地结构校验。科研质量、跨宿主行为和异常恢复仍有明显缺口。

## 1. 已复现的异常恢复缺陷：进程退出会留下锁

**位置**：`skills/research-mentor/scripts/workflow.py` 的 `locked()`。

正常退出时由 `finally` 删除 `.workflow.lock`。若持锁进程被强制结束，清理逻辑不会执行；锁中也没有 PID、主机或启动时间，后续写操作会持续报“Project is locked”。

本次在一次性临时项目中模拟持锁进程 `os._exit(17)`：进程退出后锁仍存在；随后 `checkpoint` 返回退出码 1 和锁定错误。没有改动真实研究项目。

**影响**：意外中断后无法自动恢复写入。`status` 可以读取有效状态，但不会清理锁；重新尝试 `checkpoint` 不能解决问题。

**临时处理**：先确认没有任何写入进程、备份项目并检查状态，再由维护者处理孤立锁；不要把所有锁都当作过期锁直接删除。

**建议优先级 P1**：增加持有者信息、明确的恢复命令及强制退出后的恢复测试。涉及跨主机或共享文件系统时，需要更明确的并发模型。

## 2. 模式切换不会同步项目记录

**已由代码确认**：`init --mode` 写入 `project.json`，CLI 只有 `init / template / status / validate / checkpoint / reopen`，没有模式更新命令。技能指令要求按用户最新明确要求切换模式。

**影响**：对话已切为 reviewer，状态仍可能显示初始 mentor；状态文件不足以完整还原后续模式变化。这不等于 AI 一定选错模式，而是持久记录缺少同步机制。

**建议优先级 P2**：增加带历史事件的模式更新操作，明确“项目初始模式”和“当前会话模式”。

## 3. 证据校验覆盖结构，科研语义仍依赖执行者

**设计边界**：CLI 检查证据 ID、状态、文件存在及哈希，不核实以下事项：

- 一个标记 `verified` 的来源是否真的读过，是否支持引用的结论。
- 标记 `executed` 的命令是否实际执行，结果是否由该代码产生。
- 推导是否正确、数据是否泄漏、统计单位是否独立、对照是否公平。
- `blocking_concerns` 是否完整，`resolved_concerns` 是否真的代表修复。

代码会拒绝把 planned 实验当作实证结果，但填写好状态和合法文件哈希，仍不能证明科研正确。`ready` 是结构门槛与 AI/研究者判断的组合，没有独立科学认证。

**建议优先级 P1**：增加能独立重算的数值审计、引用支持度检查、领域评测和人工抽检；保留对结构校验边界的明确表述。

## 4. 安装支持与验证范围不对称

- v1.0.0 发布验收主要覆盖 Claude 原生清单、安装链路及本地 Python 流程。
- Codex 原生命令的后续核验结果记录在 [快速安装](openai-install.md) 中；CLI 安装与桌面/云端执行属于不同验收项。
- ChatGPT Work 桌面界面、网页版工作区导入及长期会话执行，仍需要各自的真实账户端到端验收。官方格式支持不能替代这个插件在具体账户上的成功安装。
- GitHub Release 不等于插件公开目录上架。独立 Skill 安装也不等于完整插件导入。

**建议优先级 P1**：建立宿主 × 版本 × 安装方式 × 调用 × 文件执行 × 恢复的验收矩阵，记录可重复操作及实际产物。

### 本宿主观察到的同名技能重复暴露

Git 仓库根目录的兼容 `SKILL.md` 与 `skills/research-mentor/SKILL.md` 都声明 `name: research-mentor`。本会话原生插件安装后，宿主技能清单实际暴露了这两个同名入口；其中根入口会转读正式技能。尚未验证重复入口是否影响自动选择，不能据此断言所有 Codex / Work 客户端都会重复加载。

与此同时，`scripts/build_release.py` 的插件 ZIP 白名单没有包含根兼容入口，因此 Git 来源目录与发布 ZIP 的候选技能文件不同。**建议优先级 P2**：统一插件技能发现范围，保留旧版迁移入口时避免重复注册；补充 Git 安装与 ZIP 导入的技能枚举验收。

## 5. 科研效果验证集中在小型合成任务

**已知覆盖不足**：现有证据包括一个合成时序主题的流程试跑、数学/时间隔离检查及有限模式路由观察；没有跨领域代表性研究任务集，也没有与普通提示词或其他工具进行受控效果比较。

因此，目前可以说明“某些条件下能完成有证据的科研闭环”，还不能量化“提高多少科研质量、节省多少时间”，也不能据此声称能稳定产出创新论文。三种模式示例和已有少量路由任务不能当成广泛行为评测。

**建议优先级 P1**：建立覆盖实证、理论、综述、已有稿件审查和失败恢复的任务集，记录成功率、错误类型、耗时及人工复核结果。

## 6. 进度维护与工具连接仍需要较多手动协作

**实现限制**：阶段 JSON 与 `evidence.json` 主要由 AI 或研究者填写；CLI 不自动提取 DOI、不抓取论文、不启动实验、不生成 Word/LaTeX 项目。能力适配文件提供连接约定，没有把各第三方服务实现为独立可运行模块。

`project.json` 的命令写入使用锁与原子替换，但手动修改证据台账不受该锁统一管理，也没有跨文件事务。多人或多个执行者同时编辑同一项目并非已支持的工作模式。

**建议优先级 P2**：增加可选证据录入与实验记录辅助命令；以真实工具适配测试覆盖来源读取、执行、导出链路。

## 7. 版本迁移与发布材料仍需完善

**已由代码确认**：加载状态时要求 `workflow_version` 与 CLI 版本完全相同；没有状态迁移命令。升级到实现不同的后续版本前，应保留原项目和对应 CLI，不能假设新版本可以直接接续。

v1.0.0 标签及其 Release ZIP 不包含此后新增的上手指南和模式对话文档。阅读 `main` 获取最新文档，下载 v1.0.0 获取冻结实现；不要移动既有标签或悄悄替换发布包来掩盖差异。

**建议优先级 P2**：补充状态兼容策略、显式迁移与回滚说明，在后续版本发布包中包含必要使用说明。

## 后续改进顺序

1. 修复孤立锁恢复，补齐 Codex 与 Work 的真实安装/调用验收。
2. 建立科研效果与事实质量评测，加入独立可重算审计。
3. 完善模式持久化、证据编辑、版本迁移与发布文档。

这些是改进建议，不是已完成的修复承诺。一次非冻结试跑还出现过检查点返回与随后状态不一致的观察，原因未定位且后续未复现；目前继续作为待观察项保留，不宣称已修复。
